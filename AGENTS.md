# FreeRails agent guide

## Project overview

FreeRails is a Java railway strategy and management game. The application has a Swing desktop client and a game server; the launcher can start both locally. The codebase is an ongoing work in progress, so use the implementation and tests as the source of truth when older design notes differ from current behavior.

The game state is represented by `freerails.model.world.World`. Game actions are modeled as `freerails.move.Move` objects: moves are serializable, should be immutable and logically comparable, and are designed to be sent from a client to a server. `applicable` checks a move against an `UnmodifiableWorld` without changing it; `apply` performs the change on `World`. Preserve these contracts when changing game rules or networked actions.

## Repository organization

- `src/main/java/freerails/` — application code. Key areas include:
  - `client/` — Swing interface, rendering, client-side models, and launcher.
  - `controller/` — game-action and interaction logic.
  - `model/` — game state and domain objects, including terrain, track, trains, finance, and players.
  - `move/` — serializable game actions and move generators.
  - `network/` and `util/network/` — messages and connection/network utilities.
  - `scenario/` — scenario and save-game loading.
  - `server/` — server-side game model and game processing.
  - `io/` and `util/` — shared adapters and utilities.
- `src/main/resources/` — runtime resources, including client graphics, sounds and HTML views under `freerails/client/`, and scenario/game data under `freerails/data/scenario/`. Keep resource paths and references in code/data in sync.
- `src/test/java/` and `src/test/resources/` — JUnit tests and supporting data. Tests are organized along the same package boundaries as production code.
- `docs/` — Sphinx documentation in Markdown parsed with MyST, including player documentation, specifications, development notes, and artwork.
- `build.gradle`, `settings.gradle`, `gradle/`, `gradlew`, and `gradlew.bat` — Gradle build and wrapper configuration.
- `README.md`, `docs/history.md`, and `LICENSE.txt` — project overview, history, and license.

`freerails.Version` is generated by the Gradle `generateVersionInfo` task; avoid hand-editing generated version fields.

## Architecture and design principles

- Keep the model independent of the UI. Put game rules and state in the model/server-facing layers rather than in Swing views or rendering code.
- Preserve package dependency direction and avoid circular dependencies. In particular, keep low-level utilities independent of game packages and keep model logic independent of the client UI.
- Treat moves as the boundary for changes to game state. Keep applicability checks side-effect free, and make each move represent a coherent game action.
- Preserve game-state invariants. For example, track connectivity is represented across neighboring tiles; update track through track pieces/moves rather than creating one-sided connections.
- Follow established serialization and identity conventions when changing objects that cross the client/server boundary. Consider compatibility and save-game/scenario loading when changing persisted data.
- Prefer focused changes that fit existing patterns. Avoid broad formatting-only edits and unrelated refactors.

## Documentation and code style

- Write project documentation in `docs/*.md` using Markdown and MyST directives where Sphinx-specific features are needed. Update the relevant documentation when behavior or architecture changes.
- Java sources use four-space indentation, descriptive names, and Javadoc for public types and important behavior. Follow nearby files for formatting and comment conventions; do not reformat an entire legacy file for a small change.
- Add or update JUnit tests for behavior changes, especially game rules, moves, serialization, scenario data, and UI-facing behavior where applicable.
- Use the project's logger for diagnostic output rather than `System.out` or `System.err`. Avoid swallowing errors or silently substituting defaults.
- Preserve the GPL license headers and established nullability annotations where applicable.

## Build and verification

The project targets **JDK 21**. Use the Gradle wrapper from the repository root; on Windows:

```shell
.\gradlew.bat test
.\gradlew.bat check
.\gradlew.bat run
```

Run the narrowest relevant tests during iteration, then `.\gradlew.bat check` for a broad verification when practical.

For Sphinx documentation dependencies, install `docs/requirements.txt`. Follow `.github/copilot-instructions.md` for the Python interpreter to use when building HTML documentation.
